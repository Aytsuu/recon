## Required deliverables

### 1. Contract models

Create Pydantic models for the shared snake_case API contract:

- `InputMode`: `typed` and `voice`.
- `CaseStatus`: `transcribing`, `input_ready`, `clarifying`,
  `ready_for_draft`, `draft_ready`, and `failed`.
- `ClarificationStatus`: `pending`, `answered`, and `skipped`.
- Complete case response data containing:
  `id`, `input_mode`, `status`, `case_text`, `language_code`,
  `provider_name`, `service_name`, `issue_category`, `problem_summary`,
  `attempted_resolutions`, `desired_outcome`, `clarifications`, and `draft`.
- Clarification data containing:
  `id`, `field_key`, `question`, `answer`, `status`, and `position`.
- Draft data containing:
  `id`, `subject`, `body`, and `language_code`.
- Request models for case creation, case update, clarification update, and
  draft update.
- Generic success envelope:

  ```json
  { "data": {} }
  ```

- Expected-error envelope:

  ```json
  {
    "error": {
      "code": "not_implemented",
      "message": "This endpoint is reserved for a later implementation phase."
    }
  }
  ```

The models must reject malformed enum values, whitespace-only typed `case_text`,
and invalid clarification updates. An `answered` clarification requires a
non-blank `answer`; `pending` and `skipped` must not accept one.

### 2. Route modules and A1 stubs

Create and register route modules for:

```text
POST   /api/cases
GET    /api/cases/{case_id}
PATCH  /api/cases/{case_id}
POST   /api/cases/{case_id}/transcribe
POST   /api/cases/{case_id}/extract
PATCH  /api/cases/{case_id}/clarifications/{clarification_id}
POST   /api/cases/{case_id}/draft
PATCH  /api/cases/{case_id}/draft
```

Requirements:

- Keep the existing `GET /health` endpoint unchanged.
- Mount all new routes below `/api`.
- The transcription route accepts one multipart field named `audio`; add the
  minimum dependency required for FastAPI multipart parsing if it is absent.
- Every new route is a deliberate A1 contract stub and returns HTTP `501` with
  the expected-error envelope above.
- Do not return fake success payloads from unimplemented routes.
- Do not implement the A2 case state machine, AssemblyAI integration,
  extraction, clarification behavior, draft behavior, or Supabase persistence.

### 3. Repository seam

Define a small repository protocol for the operations A2 through A5 will need:

```text
create_case
get_case
update_case
create_or_update_clarification
list_clarifications
save_draft
get_draft
delete_draft
delete_case
```

Add an in-memory implementation for tests only.

The fake repository must:

- keep data isolated per test;
- return new model/data copies rather than exposing mutable stored objects;
- support direct repository contract tests; and
- not import Supabase or open a network connection.

A Supabase-backed repository belongs to A5 and is explicitly out of scope.

### 4. Fixtures and tests

Use test-first development for every A1 behavior: write the failing test, then
add the smallest implementation that makes it pass.

Add reusable JSON fixtures under `ai_engine/tests/fixtures/` for:

1. a valid `input_ready` typed case;
2. a valid `transcribing` voice case;
3. a valid `clarifying` case with one pending clarification;
4. a valid `draft_ready` case with one draft; and
5. malformed requests for blank typed input and invalid clarification updates.

Add tests that prove:

- all contract models serialize using snake_case fields;
- valid shared fixtures parse successfully;
- malformed enums, blank typed case text, and invalid clarification updates are
  rejected;
- every listed `/api` route is registered and returns the `501` error envelope;
- `GET /health` still returns its existing successful response; and
- the in-memory repository can create, load, update, save/load a draft, manage
  clarifications, and delete a case without cross-test leakage.
