## Required deliverables

### 1. Contract models

Create Pydantic models for the shared snake_case API contract:

- `InputMode`: `typed` and `voice`.
- `CaseStatus`: `transcribing`, `input_ready`, `clarifying`,
  `ready_for_draft`, `draft_ready`, and `failed`.
- `ClarificationStatus`: `pending`, `answered`, and `skipped`.
- Complete case response data containing:
  `id`, `input_mode`, `status`, `case_text`, `language_code`,
  `provider_name`, `service_name`, `issue_category`, `problem_summary`,
  `attempted_resolutions`, `desired_outcome`, `clarifications`, and `draft`.
- Clarification data containing:
  `id`, `field_key`, `question`, `answer`, `status`, and `position`.
- Draft data containing:
  `id`, `subject`, `body`, and `language_code`.
- Request models for case creation, case update, clarification update, and
  draft update.
- Generic success envelope:

  ```json
  { "data": {} }
  ```

- Expected-error envelope:

  ```json
  {
    "error": {
      "code": "not_implemented",
      "message": "This endpoint is reserved for a later implementation phase."
    }
  }
  ```

The models must reject malformed enum values, whitespace-only typed `case_text`,
and invalid clarification updates. An `answered` clarification requires a
non-blank `answer`; `pending` and `skipped` must not accept one.

## Required behavior

### Case endpoints

Implement these existing routes using the shared success envelope:

```text
POST  /api/cases
GET   /api/cases/{case_id}
PATCH /api/cases/{case_id}
```

`POST /api/cases` rules:

- A typed request requires non-blank `case_text` and creates a case with
  `status: input_ready`.
- A voice request creates a case with `case_text: null` and
  `status: transcribing`.
- Preserve optional `language_code` and `provider_name` if supplied; add these
  optional fields to `CreateCaseRequest` if they are currently absent.
- Return HTTP `201` and `{"data": <complete case>}`.

`GET /api/cases/{case_id}` rules:

- Return HTTP `200` and the complete case payload, including ordered
  clarifications and either `draft: null` or the one current draft.
- Return HTTP `404` with this error envelope when the case is absent:

  ```json
  {
    "error": {
      "code": "case_not_found",
      "message": "Case not found."
    }
  }
  ```

`PATCH /api/cases/{case_id}` rules:

- Allow updates to `case_text`, `language_code`, `provider_name`,
  `service_name`, `issue_category`, `problem_summary`,
  `attempted_resolutions`, and `desired_outcome` only.
- Do not accept a client-supplied `status`, `id`, `clarifications`, or `draft`.
- A non-blank `case_text` saved to a voice case in `transcribing` transitions it
  to `input_ready`.
- A material change to `case_text`, `provider_name`, `service_name`,
  `issue_category`, `problem_summary`, `attempted_resolutions`, or
  `desired_outcome` deletes any existing draft.
- After invalidating a draft, set the case to `ready_for_draft` only when
  `provider_name`, `problem_summary`, and `desired_outcome` are all non-blank
  and no clarification is pending; otherwise set it to `input_ready`.
- Return the updated complete case payload or the same `404` error envelope.

### Clarification endpoint

Implement this existing route:

```text
PATCH /api/cases/{case_id}/clarifications/{clarification_id}
```

Rules:

- Return `404 case_not_found` when the parent case does not exist.
- Return HTTP `404` with `clarification_not_found` and message
  `"Clarification not found."` when the clarification is not part of that
  case.
- For `status: answered`, require the existing request-model validation and copy
  the answer to its matching case field:
  `provider_name`, `problem_summary`, or `desired_outcome`.
- For `status: skipped`, leave the matching case field unchanged.
- When one or more clarifications remain pending, set the case to `clarifying`.
- When none remain pending, set the case to `ready_for_draft` only if all three
  required fields are non-blank; otherwise set it to `input_ready`.
- Return the updated complete case payload.

## State boundaries

Only A2 state transitions are in scope:

```text
typed creation                    -> input_ready
voice creation                    -> transcribing
reviewed voice case_text          -> input_ready
pending clarification remains     -> clarifying
all required fields + no pending  -> ready_for_draft
material edit after a draft       -> draft removed, then input_ready or ready_for_draft
```

Do not implement `draft_ready` transitions, draft generation, extraction,
transcription, AssemblyAI, Supabase, provider routing, external sending, or
authentication. The corresponding routes remain HTTP `501` with the A1
`not_implemented` envelope.
